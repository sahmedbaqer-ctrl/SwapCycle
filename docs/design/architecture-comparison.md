# Architecture Comparison – Layered vs Microservices ## Styles compared- **Layered:** one application split into three layers. The presentation layer holds the web pages, REST controllers and auth middleware. The business layer has one module per feature. The data access layer holds the repositories over one PostgreSQL database. Each layer only calls the layer below it.- **Microservices:** each feature (Accounts, Listings, Exchange, Messaging and so on) runs as its own service with its own database. Services talk over the network behind an API gateway. ## Comparison | Criterion | Layered | Microservices | |---|---|---| | Scalability | Run more copies of the whole app behind a load balancer. 100 concurrent users (NFR 1.1) fits on one server | Each service scales on its own. Stronger, but SwapCycle doesn't need it yet | | Security | One auth middleware guards every request, so access rules for private messages (NFR 2.1) and admin-only reports (NFR 2.3) sit in one place | Every service checks tokens itself, and every link between services is another point of attack | | Maintainability | One codebase and one database. Each feature module changes on its own | Small codebases, but one swap (Exchange → Completion → Rating) crosses three services | | Team fit | Module boundaries match our feature owners. One repo, one deployment | Six students would run six services, pipelines and databases | Completing a swap (FR 2.7) updates the exchange, both users' records and their ratings. With one database that is a single transaction. With microservices it needs a saga, which we can't build in one sprint.
